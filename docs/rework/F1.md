## Why
The 48-hour hold, the 14-day loan and the 5/10 borrow limits are hard-coded in about 10 places:
`services.py`, the PDFs (`documents.py`, `idcard.py`), notification and activity text,
`RegisterView`, `seed_demo` and the UI copy. The owner wants admins to change them, and wants
students to be able to renew a loan.

## Backend

### `LibrarySettings` (singleton model + migration)
- Fields, with defaults equal to today's rules:
  - `hold_hours` 48 (1–168);
  - `loan_days` 14 (1–90);
  - `max_renewals` 1 (0–5);
  - `member_borrow_limit` 5 (1–50);
  - `staff_borrow_limit` 10 (1–50);
  - `reminder_days_before_due` 2 (0–14), used by F2;
  - `updated_at`;
  - `updated_by` (FK, SET_NULL).
- `LibrarySettings.get()` returns row pk=1, creating it if missing.
- Constant `RENEW_WINDOW_DAYS = 3` in `services.py`. It is not a setting.

### Endpoints
- **`GET /api/settings`:** anyone gets `holdHours`, `loanDays`, `maxRenewals`, `renewWindowDays`.
  Admins also get `memberBorrowLimit`, `staffBorrowLimit`, `reminderDaysBeforeDue`, `updatedAt`
  and `updatedBy`.
- **`PATCH /api/settings`:**
  - admin only;
  - DRF validation with the bounds above. An out-of-range value is a 400 with the standard
    `invalid` body;
  - log `SETTINGS_CHANGED` with the changed fields as params;
  - returns the admin view.

### Use the settings everywhere
- `services.py`:
  - approval and `_hand_to_queue` use `hold_hours`;
  - pickup uses `loan_days`.
  - **Changing a setting never moves existing deadlines.**
- Notification, activity and PDF text that says "48 hours" or "14 days" takes the number as a
  param or argument. The translated `notif.*` and `activity.*` strings gain `{hours}` / `{days}`.
  Keep the English `detail` / `message` accurate as well.

### Borrow limits
- `UserProfile.max_borrow_limit` becomes nullable. **`null` means "use the default for my role"**
  from the settings; a number is a personal override.
- A data migration sets existing profiles whose value equals their role's old default
  (5 for members, 10 for staff and admin) to `null`, and keeps any other value as an override.
- Add a `UserProfile.effective_borrow_limit` property and use it everywhere:
  - `create_request`;
  - the serializers (`maxBorrowLimit` and `memberMaxBorrowLimit` now report the effective value);
  - the PDFs;
  - registration and `seed_demo`, which stop writing 5 or 10.

### Renewal
- **Transition:** `"renew": [Status.BORROWED]`. `services.renew(actor, record)` locks the book,
  then the record (same order as elsewhere) and checks, in this order:
  1. The actor is the owner, or staff/admin. Otherwise 403 `forbidden`.
  2. The transition is allowed. An OVERDUE, PENDING or other record is a 409 `invalid_transition`.
  3. The member has no other OVERDUE loan, otherwise `overdue_block`.
  4. `renewal_count < max_renewals`, otherwise `renew_limit {max}`.
  5. Nobody is waiting for the book (an active reservation exists), otherwise `renew_queue`.
  6. The due date is at most `RENEW_WINDOW_DAYS` away, otherwise `renew_too_early {days}`.
- **On success:**
  - `due_date += loan_days`;
  - `renewal_count += 1` (new field on `BorrowRecord`, default 0, with a migration);
  - log `LOAN_RENEWED`;
  - **when staff renewed on the member's behalf**, notify the member with
    `loan_renewed {title, dueDate}`.
- **Endpoint:** `POST /api/borrow-records/<id>/renew` returns the record.
- **Serializer:** `renewalCount`.
- **Error and notification codes** need translations in EN, FR and AR. The existing
  "every code is translated" test enforces it.
