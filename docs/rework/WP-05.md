(rate limits, end of this file). Model: **Sonnet · high**.

**Contract:** `backend/library/test_auth_cookies.py` (14 tests fail today, by design) and the

Done when all backend tests pass, lint, `tsc -b` and both builds pass, and the browser checks

## Why

Today both JWTs sit in `localStorage` (`lb_access`, `lb_refresh`). Any script that runs on the
page, such as an XSS bug or a compromised dependency, can read the 7-day refresh token and use it
from anywhere. After this change:
- the refresh token is an **httpOnly cookie** that scripts cannot read;
- the access token lives **only in memory**, lasts 10 minutes, and is never persisted.

## Deployment constraint: the API must be same-site with the frontend

Safari and Firefox block cookies that belong to a different site (third-party cookies), and
`*.vercel.app` is on the Public Suffix List, so `app.vercel.app` → `api.onrender.com` is
cross-site. Supported topologies:

1. **Same origin (default and recommended):** the frontend's host proxies `/api` to Django.
   This means the Vite proxy in dev, the Vercel rewrite documented in `DEPLOYMENT.md`, or an nginx
   `location /api/`. No CORS is needed, and the cookie can be `SameSite=Strict`.
2. **Same site, different subdomain** (`library.example.edu` + `api.library.example.edu`):
   needs `CORS_ALLOW_CREDENTIALS = True`, `SameSite=Lax`, and `credentials: "include"` on fetch.

A cross-site API (`VITE_API_URL` on another registrable domain) is **no longer supported**.
Update `DEPLOYMENT.md`: make the Vercel rewrite the primary real-backend setup, and explain why
in one sentence.

## Backend

### Settings (`config/settings.py`)
```python
SIMPLE_JWT = {
    "ACCESS_TOKEN_LIFETIME": timedelta(minutes=10),
    "REFRESH_TOKEN_LIFETIME": timedelta(days=7),
    "ROTATE_REFRESH_TOKENS": True,
    "BLACKLIST_AFTER_ROTATION": True,
    "UPDATE_LAST_LOGIN": True,
}
AUTH_REFRESH_COOKIE = {
    "name": "lb_refresh",
    "path": "/api/auth",
    "samesite": os.environ.get("AUTH_COOKIE_SAMESITE", "Strict"),   # "Lax" for the subdomain setup
    "secure": not DEBUG,
    "domain": os.environ.get("AUTH_COOKIE_DOMAIN") or None,         # only for the subdomain setup
}
AUTH_CSRF_HEADER = "HTTP_X_LIBBORROW_CSRF"
CORS_ALLOW_CREDENTIALS = True
CORS_ALLOW_HEADERS = (*default_headers, "x-libborrow-csrf")         # from corsheaders.defaults
```
- Add `rest_framework_simplejwt.token_blacklist` to `INSTALLED_APPS`. Its migrations come with
  the package, so `makemigrations --check` must still be clean.
- In production, refuse to start if `samesite` is `"None"`; it would only work with
  third-party cookies, which this design rules out.
- Document `AUTH_COOKIE_SAMESITE` and `AUTH_COOKIE_DOMAIN` in `DEPLOYMENT.md`.

### Views (new `library/auth_views.py`, routed in `urls.py`)
- `POST /api/auth/login`:
  - Validate with `TokenObtainPairSerializer`.
  - Return `{"access": ...}` only.
  - Set the refresh token as the cookie, with `max_age` = refresh lifetime in seconds,
    `httponly=True`, and path/samesite/secure/domain from `AUTH_REFRESH_COOKIE`.
  - Bad credentials: 401 with no cookie. Keep the `username` field, which is the email.
- `POST /api/auth/refresh`:
  - 403 if the `X-LibBorrow-CSRF` header is missing.
  - 401 if there is no cookie. Ignore any `refresh` field in the body.
  - Otherwise run `TokenRefreshSerializer` with the cookie value. It rotates and blacklists
    the old token, and rejects deactivated users.
  - Return `{"access"}` and set the new refresh cookie.
  - On an invalid or expired token, return 401 **and delete the cookie**.
- `POST /api/auth/logout`:
  - 403 without the header.
  - Blacklist the cookie's token if it is present and valid, and ignore errors.
  - Delete the cookie (same path and domain).
  - Return 204, also when there is no session.
- Put the header check and the cookie set/delete code in small helpers, used by all three views.
- Bearer authentication for every other endpoint stays as it is. SimpleJWT already rejects a
  refresh token used as a Bearer token, because of its token type; the test pins that.

## Frontend

### `src/api/client.ts`
- Keep the access token in a module variable. Export `getAccessToken()`; nothing else reads it.
  Remove every `localStorage` read and write of `lb_access` and `lb_refresh`.
- On module load, run a one-time cleanup: `localStorage.removeItem("lb_access")` and
  `removeItem("lb_refresh")` in try/catch. Existing users sign in again once.
- `refreshAccess()`:
  - `POST /auth/refresh` with the `X-LibBorrow-CSRF: 1` header and `credentials: "include"`.
  - **Single-flight within the tab:** callers share one in-flight promise.
  - **Across tabs**, serialize with the Web Locks API: `navigator.locks.request("lb-auth-refresh", ...)`.
    Rotation makes the old cookie invalid, so two tabs refreshing in parallel would log one of
    them out. Once the lock is acquired, the browser already holds the newest cookie.
  - Fall back to no lock where `navigator.locks` is missing.
- `api()`: when the response is 401 → refresh once → retry once. On a second failure, clear
  memory and dispatch `lb:logout`, as today.
- Export one `authFetch(url, init)` that adds the Bearer header and applies the same
  refresh-and-retry, plus `credentials: "include"`. Use it for the three raw fetches in
  `src/api/index.ts` (`updateWithCover`, `downloadFile`, `downloadIdCard`).
- `auth.login()` stores the access token in memory.
- `auth.logout()` calls `POST /auth/logout` (header plus credentials), clears memory, and posts
  `"logout"` on a `BroadcastChannel("lb-auth")`. On receiving it, other tabs clear memory and
  dispatch `lb:logout`. Wrap the BroadcastChannel in a feature check.
- `auth.restore()`: called once at startup. It tries `refreshAccess()` and resolves to true or
  false. It replaces `isLoggedIn()`.

### `src/auth/AuthContext.tsx`
On mount, `await auth.restore()`. If it returns true, load `/users/me`; otherwise set `me = null`.
Keep `loading` true until this settles, so the route guards don't redirect too early on reload.
`logout` awaits `auth.logout()`.

### Demo (`src/api/demo.ts`)
There are no real cookies in the demo, so emulate the jar:
- `/auth/login` stores the refresh token under the demo-only key `lb_demo_refresh` and
  returns `{access}`.
- `/auth/refresh` and `/auth/logout` read and clear that key, require the header, rotate
  the token, and reject reuse of a rotated token. Keep the set of revoked tokens in demo state.
- `resetDemo()` also removes `lb_demo_refresh`.
- Bump `DEMO_STORAGE_KEY` if the state shape changes.

## WP-07: Rate limits (same pass)
DRF throttling with `ScopedRateThrottle`:
- `auth_login`: 10/min
- `auth_register`: 5/hour
- `auth_refresh`: 30/min

Register needs its own scope because the staff invite code is guessable by brute force on that
endpoint. Rates go in `REST_FRAMEWORK["DEFAULT_THROTTLE_RATES"]`. Behind a proxy, DRF keys on
`REMOTE_ADDR`; set `NUM_PROXIES` from an env var `DJANGO_NUM_PROXIES` (default 0) and document it.

Add tests in `test_auth_cookies.py`'s style, in a new file `test_throttling.py`:
- the 11th login in a minute returns 429;
- register throttles separately.

Clear the cache in `setUp`, and use `override_settings` for small rates if that's simpler.
